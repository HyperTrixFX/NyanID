# 权限与封禁系统

## 1. 权限系统

### 权限节点

权限以「节点字符串」表示（`utils/System/PermissionNodes`）：

| 节点 | 含义 |
| --- | --- |
| `*` | 根权限，拥有全部权限 |
| `minecraftproxy.admin` | 代理管理（HTTP 面板 + 全部代理命令） |
| `minecraftproxy.command` | 代理命令前缀（授予全部代理命令用 `minecraftproxy.command.*`） |
| `minecraftproxy.command.server` | `/server` |
| `minecraftproxy.command.ip` | `/ip` |
| `minecraftproxy.command.list` | `/list` |
| `minecraftproxy.command.status` | `/status` |
| `minecraftproxy.command.broadcast` | `/broadcast`（别名 `/bc`） |
| `minecraftproxy.command.kick` | `/kick` |
| `minecraftproxy.command.ban` | `/ban` |
| `nyanid.admin.cctop` | 站内管理员标记 |
| `nyanid.admin.user` | 用户管理（V3 `/api/zako/v3/users`） |
| `nyanid.admin.ticket` | 工单管理（V3 `/api/zako/v3/tickets`） |

### 匹配规则（`services/PermissionService`）

1. 根节点 `*` → 全部通过。
2. 精确匹配：授予了 `minecraftproxy.command.server` 就只对该节点生效。
3. 通配：授予 `minecraftproxy.command.*` 后，其下所有子节点都通过。

### 数据表

- `Permission`：权限节点目录（`id`、`code`、`name`）。`code` 约定：`-1`=root、`1354`=proxy、`0`=d_user、`1`=a_user。
- `UserPermissions`：用户授权（复合主键 `(uid, permission)`，一条记录 = 一个用户拥有一个节点）。

### 授予 / 回收

**HTTP**（需 `minecraftproxy.admin` 权限，见 [04-API接口文档](./04-API接口文档.md)）：

```
GET    /api/zako/v3/proxy/permissions?uid=<uid>
POST   /api/zako/v3/proxy/permissions?uid=<uid>&node=<节点>
DELETE /api/zako/v3/proxy/permissions?uid=<uid>&node=<节点>
```

**控制台**：

```text
/op <uid>     # 授予根权限 *
```

（按节点回收用 HTTP `DELETE /api/zako/v3/proxy/permissions?uid=&node=`。）

### Minecraft 玩家 → 权限

`PlayerCommandSender.hasPermission` 用玩家 Minecraft UUID 解析 NyanID UID（先查 `Yggdrasil.uuid`，再查 `Accounts.bind`），再走节点匹配。正版（Mojang）玩家没有 NyanID 账号，默认无任何代理权限。

## 2. 封禁系统

### 封禁类型（`BanUserList.Type`）

| 值 | 含义 |
| --- | --- |
| 5 | 禁止登录游戏（可登录网站）——游戏内 `/ban` 默认 |
| 6 | 死封（永久、全站） |
| 4 | 门户锁 |
| 1/2/3 | 限制昵称 / OAuth 登录 / 头像 |
| -1 | 安全警告 |

### 封禁目标类型（`TargetType`）

| 值 | 含义 |
| --- | --- |
| `0` | NyanID UID（Yggdrasil 玩家） |
| `1` | Mojang UUID（正版玩家） |

判定逻辑（`ProxyBanService.resolveTarget`）：玩家 Minecraft UUID 能在 `Yggdrasil` 反查到 NyanID UID → 封 UID；否则 → 封 UUID（去连字符）。

### 字段

- `BanID`：13 位封禁编号。
- `Reason`：原因。
- `isActive`：是否生效。
- `BanTime` / `BannedBy`：封禁时间 / 操作者。
- `ExpireTime`：解封时间；`null` = 永久。

### 自动解封（低资源）

- 登录鉴权查询本身带 `ExpireTime IS NULL OR ExpireTime > now` 过滤，过期封禁不会拦截。
- `BanExpiryScheduler` 每 60 秒执行一条批量 `UPDATE`，把已过期的封禁置为 `isActive=false`（表数据清理，非逐条轮询）。

### 游戏内封禁命令

```text
/ban <玩家> [原因] [时长]
```

- 时长：`30s` / `30m` / `2h` / `7d` / `1w`；缺省永久。
- 默认 `Type=5`，封禁后立即踢下线，并在下次登录拦截。

### 登录拦截

`InitialHandler.finishLogin` 在创建连接前调用 `ProxyBanService.findGameBan`，命中则发送封禁踢出画面（含原因 / 解封时间 / 封禁 ID）。

### 活跃异常（只读状态）

- 「活跃异常」= 该 uid 存在 `isActive=true` 的封禁记录（`BanUserRepository.existsByUidAndIsActiveTrue`）。
- 活跃异常账号**仍可进行 Web 登录**（`UserServices.login` 与 `AuthenticateCheck` 拦截器均不再拦截封禁账号），但账号进入**只读**状态，禁止任何资料/安全修改：
  - 改昵称 / 用户名 / 简介 / 绑定 / 头像 → `UserDataServices.ActionMethod`、`PutMethod` 返回 403。
  - 开启 / 关闭 2FA → `UserSecurityServices.Open2FA`、`Close2FA` 返回 403。
  - 找回 / 重置密码 → `UserDataServices.ForgetPwdStep1`、`ForgetPwdStep2` 返回 403。
- 目的：让被封用户仍能登录查看信息并提交禁封申诉（type=1 工单），但无法借机改动账号。
- 注意：这里只放开 **Web 登录**；游戏（Minecraft）登录仍按封禁类型由 `ProxyBanService.findGameBan` 拦截。
