# 13 - 安全审计与踩坑总结

> 本文为 NyanID 项目一次全量安全审计（静态代码审查 + 对运行实例 `http://localhost:8081` 的动态验证 + 数据库抽查）的结论汇总与踩坑复盘。
> 所有结论均附 `文件:行号` 证据，并区分「已核实」「潜在（当前数据未触发）」「待核实」。
> 审计期间**未修改任何业务代码**；修复需另行确认后实施。

---

## 0. 审计概览

- 范围：`src/main/java` 全部 269 个文件 + `src/main/resources` 配置 + `pom.xml` 依赖 + `config/application.yml` 运行配置 + 运行实例动态探测 + `awaa1111` 库抽查。
- 方法：6 个领域并行审计（认证/会话、Yggdrasil 协议、V3 管理授权、业务逻辑、Netty 代理、注入/密钥/依赖）+ 人工交叉核对 + 动态复现。
- 结论：**未发现 SQL 注入、命令注入、用户可控 SSRF、可利用路径遍历、网络面 fastjson autoType RCE**；但存在多处**严重/高危**的密钥管理、密码学、授权与业务逻辑缺陷。

### 动态验证结论（http://localhost:8081）
1. `/actuator` 仅暴露 `health`（`/env`、`/beans`、`/heapdump` 均 404）——低危，非高危暴露。
2. V3 端点未授权访问正确返回 401/403（`AuthenticateCheck` 生效）。
3. **CORS 反射任意 Origin + `Allow-Credentials:true` 已实测复现**（`Origin: http://evil.example.com` 被原样反射）。
4. 数据库抽查：`ban_user_list` 现有 1 条 `Type=6` 且 `is_active=1` 的**死封**记录（证明「死封不阻断代理登录」当前即可被利用）；当前**无** `Type=5/0` 记录（`LEVE450TRUE` 优先级缺陷为潜在）。

## 1. 漏洞清单（按严重度）

### 1.1 严重（Critical）

#### C1 密码存储 = 无盐、无迭代的 HMAC-SHA256(硬编码密钥)
- 位置：`services/UserServices.java:165,311`、`server/YggdrasilServer/Authserver/Authserver.java:122`、`services/UserDataServices.java:126`、`utils/utilset.java:309-320`、密钥 `src/main/resources/application.cfg:78-80`
- 说明：口令哈希 = `HMACSHA256(encryptionKey, password)`。无盐（相同口令全库同哈希）、无工作因子（HMAC-SHA256 极快，GPU 可秒级爆破）、密钥硬编码进源码配置。
- 利用：拿到仓库/配置或数据库任一者即可离线批量爆破全库口令；无盐还可预计算彩虹表一次覆盖所有账号。
- 修复：改用 bcrypt / scrypt / Argon2id（内置随机盐 + 高成本因子），彻底移除硬编码密钥，改用环境变量/密钥管理注入。

#### C2 硬编码密钥与凭据（部分提交进 git）
- 位置：`src/main/resources/application.cfg`（被 git 跟踪）：MySQL `nyanid/nyanid`（`:28-30`）、Redis `nyanid123`（`:36`）、SMTP `bjdbjd@bjdbjd.net/bjdbjd`（`:44-45`）、`encryptionKey`（`:78-80`）、Turnstile 测试密钥 `1x00000000000000000000AA`（`:73-74`）、DeepSeek（`:113`）。另 `config/application.yml`（git 忽略但位于仓库目录）含**真实**凭据：DB `awaa1111`、Redis `nyanid123`、QQ 邮箱授权码、Microsoft 密钥、**完整 RSA 私钥**、DeepSeek 真实 key `sk-8a05…`、`encryptionKey` 全量、`sm4Key`。
- 利用：仓库/镜像/备份/制品任一泄露即 DB、Redis、邮箱、外置登录签名密钥全盘沦陷。
- 修复：所有凭据/密钥外置到环境变量或 Secret 管理，仓库内仅保留占位符；轮换已泄露密钥；清理 `target/`、`Data/` 等产物中的真实密钥。

#### C3 Redis 序列化器显式开启 fastjson2 autoType（潜在反序列化 RCE 面）
- 位置：`utils/RedisUtils/FastJson2JsonRedisSerializer.java:33`（`WriteClassName`）、`:43`（`JSON.parseObject(str, clazz, JSONReader.Feature.SupportAutoType)`），注册于 `utils/RedisUtils/RedisConfig.java:24-27`
- 说明：Redis value 按 JSON 内 `@type` 实例化类，正是 fastjson(2) autoType 反序列化 RCE 攻击面（classpath 上含 spring/netty/quartz/bcpkix 等 gadget 源）。
- 利用：若攻击者可向 Redis 写入恶意 JSON（弱口令 `nyanid123`、Redis 暴露、或本地控制台 `/redis` 命令）→ 注入 `@type` 指向 gadget 触发 RCE。
- 修复：去掉 `SupportAutoType`，改为 `JSON.parseObject(str, clazz)` 类型化反序列化；Redis 强口令 + 仅绑定内网 + 不对外暴露。

## 2. 已核实排除的误报（无此漏洞）

- **无 SQL 注入**：repository/`SqlService` 全部参数化（`?1`/`:keyword`），无字符串拼接。
- **无命令注入**：无 `ProcessBuilder`/`Runtime.exec`；控制台 `/op` 只写 DB 权限，`/systemctl` 只写 Redis。
- **无用户可控 SSRF**：出站目标均为固定端点或已配置后端，客户端无法指定任意目标。
- **无可利用路径遍历**：材质/头像路径有 `startsWith(baseDir)` + 32 位 hex 校验，材质文件名用 SHA-256 内容哈希。
- **网络面无 fastjson autoType RCE**：网络面 `parseObject` 均为默认（autoType 关闭）；仅 Redis 序列化器开启了 `SupportAutoType`（见 C3）。
- **`toSafeUserJson` 确实脱敏**：未泄露 password/SecretKey/GithubAccessToken。
- **`utilset.decrypt` 吞异常返回 null 的所有调用点均判空**：当前不可借此绕过认证。
- **`getMyTicket` 归属校验正确**、管理员端点权限节点校验存在、`GlobalExceptionHandler` 不回显堆栈。
- **客户端无法直连滥用 BungeeCord 通道**：`UpstreamBridge.java:244-246` 已丢弃客户端方向的 BungeeCord 频道。

## 4. 踩坑总结（复盘）

1. **口令散列不是加密**：用 `HMAC-SHA256(固定key, password)` 代替 bcrypt/argon2，是本次最严重缺陷——无盐、无迭代、密钥硬编码，一次泄露全库可离线爆破。散列必须用自带盐与成本因子的专用算法。
2. **密钥/凭据必须外置**：`application.cfg`（被 git 跟踪）与 `config/application.yml` 混放占位与真实密钥，且真实 RSA 私钥、DeepSeek key、邮箱授权码都在仓库目录里。约定：仓库只留占位符，真实值走环境变量/Secret。
3. **安全令牌要用 `SecureRandom`**：`java.util.Random`（48 位 LCG）生成了 accessToken/验证码/clientToken/重置码；TOTP 种子还用了 `setSeed(时间戳)`，直接毁掉了 `SecureRandom` 的熵。凡是令牌/验证码/密钥，一律 `SecureRandom` 且不要手动 `setSeed`。
4. **反序列化默认关 autoType**：Redis 序列化器显式开了 `SupportAutoType` + `WriteClassName`，叠加弱 Redis 口令就是 RCE 面。fastjson 系列务必用类型化 `parseObject(str, Clazz)`。
5. **CORS 不要「反射 Origin + credentials」**：反射任意 Origin 且带 `Allow-Credentials:true` 等于关闭同源策略；`allowedOriginPatterns` 配置了却没用。
6. **布尔条件别用 `&&`/`||` 想当然**：Turnstile 校验 `!success && !action.equals(...)` 应为 `||`；`Authserver` 私钥/公钥加密方向写反。逻辑分支要写单测覆盖。
7. **SQL/JPQL 的 AND/OR 必须显式分组**：`LEVE450TRUE`（`... AND Type=4 or Type=5 or Type=0`）与 `AccountsRepository.find` 都被解析成 `(A AND B) OR C`，跨用户匹配。有多个 `OR` 就加括号。
8. **Spring Data 派生查询 `Is` 前缀歧义**：字段名 `isActive`/`IsDeveloper` 生成 `findByIsActiveTrue`/`existsBy...IsActiveTrue` 会被误解析，运行时抛异常。用显式 `@Query` 规避（本项目早前已踩过）。
9. **身份标识不要「可跨账号复用」**：`clientToken` 复用 + `ClientId` 做主键，导致换账号登录返回上一账号的 accessToken。唯一标识若会被跨账号复用，必须同时按归属（uid）过滤。
10. **封禁类型矩阵要单一事实来源**：游戏登录闸门只匹配 `Type=5/20`，却存在 `Type=6` 死封记录；`LEVE450TRUE` 又涉及 `Type=4/5/0`。封禁类型、查询口径、拦截点三处必须一致。
11. **拦截器要「注册 + 路径正确 + 逻辑正确」三连**：`PermissionsCheck` 恒 `return false` 且从未注册（死代码）；2FA 限流注册在 `/login/2fa` 而实际路径是 `/2fa`。集中鉴权失效后，鉴权散落各处手写，极易漏。
12. **OAuth 的 state/nonce 必须校验**：生成后从不比对就是登录 CSRF。
13. **解压/数组长度必须有上限**：`PacketDecompressor` 与 `DefinedPacket.readArray` 对 `uncompressedSize`/长度不设上限，攻击者可控即 OOM。任何「长度 → new byte[len]」都要设上界并校验符号。
14. **离线模式的 UUID 不能当身份**：离线 UUID = 用户名确定性派生，直接参与权限与 ip_forward 就是「知道用户名=拥有其身份」。离线模式与权限/ip_forward 必须解耦。
15. **IP 不能来自可伪造的 XFF**：限流/封禁的 IP 取自 `X-Forwarded-For`，攻击者轮换 XFF 即可绕过。仅信任白名单代理，或直接忽略 XFF。
